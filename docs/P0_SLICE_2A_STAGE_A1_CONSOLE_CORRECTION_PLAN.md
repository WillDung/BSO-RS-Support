## 1. Exact offline reproduction

The [canonical generator](../scripts/New-BsoRsCandidateConsoleEnvironmentConfig.ps1) serializes the bound configuration as UTF-8 without a BOM, hashes those exact bytes, and places the first 12 hexadecimal characters of that hash in the environment-script URL in the [canonical HTML](../solutions/CandidateConsole/WebResources/os_/bso/candidate-console.html). The source configuration is intentionally unconfigured; it is not the bound environment configuration.

The pair was independently generated **in memory**, not by substituting the previously reported digest. The reproduction read the static target-binding fields from the guarded helper without executing it or printing the fields, applied the generator's DEV policy defaults, used the same ordered PowerShell `ConvertTo-Json -Compress` serialization and source here-string, and encoded the resulting configuration as UTF-8 without a BOM. It calculated the configuration SHA-256 from those newly generated bytes **before** deriving the HTML token. Only then did it compare the 570 generated configuration bytes with the separately retained, access-controlled historical configuration artifact: they matched **byte for byte**, not merely by reported digest. The historical hash was an assertion, never an input to the transformation.

The actual generator was not executed because it writes files. No cached token file was read; no generated configuration or HTML was written to the repository or to a scratch file. Only hashes and non-secret cache-version tokens are reported here; the binding and configuration bytes are not reproduced.

## 3. Exact proposed one-resource request sequence

The following are request templates, **not commands to run now**. Authentication is supplied only by the separately approved managed request context. Resolve every placeholder privately at execution; never place an actual origin, identity, authorization token, ETag, or Base64 content in the plan or journal.

Microsoft Learn's *WebResource table/entity reference* documents `PATCH /webresourceset(webresourceid)` and Base64 `content`; *Perform conditional operations using the Web API* documents conditional updates. Those general contracts do **not** by themselves establish the target's unpublished-layer ETag semantics required in section 2.

### 3.1 Update the existing HTML once

After all gates pass, send exactly one conditional PATCH, with the exact current-layer ETag, not `*`. The body contains **only** `content`; it is the Base64 encoding of the verified generated HTML bytes, not the configuration.

```http
PATCH <APPROVED_ORIGIN>/api/data/v9.2/webresourceset(<HTML_WEBRESOURCE_OBJECT_ID>) HTTP/1.1
Accept: application/json
Content-Type: application/json; charset=utf-8
OData-Version: 4.0
OData-MaxVersion: 4.0
If-Match: <FRESH_CURRENT_UNPUBLISHED_ETAG>
MSCRM.SolutionUniqueName: os_sr_bso_rs_support

{"content":"<BASE64_OF_VERIFIED_EXPECTED_HTML_BYTES>"}
```

Reserve the dispatch before sending; disable client and transport retries and redirects. A normal no-representation response is expected to be HTTP 204, but acknowledgment is not readback. A `412`, rejection, timeout, lost response, unexpected response, or failed readback means **stop; no retry and no automatic restore**. Reconcile read-only and preserve the journal for a new decision.

After an acknowledged PATCH, independently read all six current/unpublished and published definitions. Require current HTML `699afe50…03e25`, published HTML still `b0d3cede…086e`, and both layers of the other five resources unchanged. Reconfirm target, Solution membership, disabled gate, exact HTML identity, and the exclusive change window. Any discrepancy stops before publication.

### 3.2 Publish that HTML once

Resolve `HTML_WEBRESOURCE_OBJECT_ID` below to the freshly rechecked, unbraced canonical GUID from the HTML **`webresourceid`** and the matching type-61 Solution component `objectid`. Validate the XML and assert exactly one `webresources` collection containing exactly one `webresource`; no other component nodes are permitted. Then, only under separate publication authorization, send exactly one request:

```http
POST <APPROVED_ORIGIN>/api/data/v9.2/PublishXml HTTP/1.1
Accept: application/json
Content-Type: application/json; charset=utf-8
OData-Version: 4.0
OData-MaxVersion: 4.0

{"ParameterXml":"<importexportxml><webresources><webresource>HTML_WEBRESOURCE_OBJECT_ID</webresource></webresources></importexportxml>"}
```

Microsoft Learn's `PublishXml` action reference describes publication of specified components; the object ID must be substituted before dispatch. The [existing builder and tests](../tests/CandidateConsole.Tests.ps1) use WebResource IDs, not unique-version IDs or Solution-component row IDs. This payload explicitly excludes `srapp`, all app modules, the sitemap, entities, and every other WebResource. **Do not use `PublishAllXml` or `pac solution publish`.** Expect one acknowledged response and zero retries; any ambiguous or unsuccessful outcome stops with read-only reconciliation only.

The [existing deploy helper](../scripts/Deploy-BsoRsCandidateConsole.ps1) must not be assumed safe or executed for this correction. Its inventory and `ValidateSet` describe five resources and reject inventory drift, whereas Slice 2A has six; its publish-only mode rejects replacement content, and its source-ahead mode requires an older pinned HTML/JavaScript pair. Its PATCH path also obtains an ETag from an ordinary resource GET before separately reading the current layer; that does not prove the required current-layer conditional guarantee. Its static tests do not establish six-resource or live ETag behavior. Do not weaken its guards or run a write-capable helper as a dry run.

## 5. Rollback and ambiguity

Rollback is **not automatic** and is not authorized by approval of the forward PATCH or publish. It requires a separate decision and authorization, a fresh exact-target/identity check, verified protected `P0` and `C0` copies, a fresh current-layer conditional token with the same proven semantics, an enforceable exclusion window, and exact readback of current and published state. If any result or state is ambiguous, perform only authorized read-only reconciliation; do not retry, publish, or restore automatically.

| Definitely reconciled state before any separately approved rollback | Bounded restoration strategy |
|---|---|
| PATCH acknowledged and verified; publish not dispatched: current is expected new HTML, published is exactly `P0` | Conditionally restore **`C0`** to current once. Do not publish: that could change an already-correct published layer. Independently verify published `P0` and current `C0`. |
| PATCH and publish acknowledged and verified: both layers contain expected new HTML; normal preflight established `P0 = C0` | Conditionally restore **`P0`** to current once, then publish only the same HTML once, under a separately authorized rollback publication. Independently verify published `P0` and current `C0`; the restored old token reintroduces the known Stage A mismatch. |
| Captured pre-update `P0 != C0` | The normal correction above must already have stopped. A different, separately reviewed recovery would need to prove supported layer semantics: conditionally stage `P0`, publish only HTML, verify published `P0`, then conditionally stage `C0` **without another publish**, and verify both layers independently. This could require two PATCHes and one publish; no such sequence is authorized or proven here. If exact preservation of both layers cannot be demonstrated, do not attempt it. |
| Outcome, concurrent change, ETag, or either layer is uncertain | Stop. Preserve evidence and seek a new bounded decision; do not replay a request or assume a compensating write is safe. |

One publication normally makes the staged current content published; it cannot be assumed to restore two different captured layers. Even exact definition restoration does not prove every browser cache has reverted. Any served-layer rollback verification has the same separate browser-approval and side-effect boundary as section 4.
