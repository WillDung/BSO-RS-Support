## Phase 4E Round 1 Reschedule and Cancellation (28 October 2026)

The existing `os_sr_intv` table is reused; no second schedule/result table was created. The schedule lifecycle Choice is optional for compatibility with existing rows and contains Proposed, Scheduled, Cancelled, and Superseded. An unset value is rendered as Scheduled. The Candidate Console shows all Round 1 schedule rows newest first and preserves cancellation/reschedule reasons, lifecycle timestamps, and result evidence. Resulted Pass/Fail schedules and terminal Candidate statuses do not expose reschedule/cancel actions; ambiguous/multiple-current states fail closed.

For rescheduling, the UI requires a new date/time, a visibly selected TA and Location, and a reason. It marks the old schedule Superseded and confirms the write by readback, creates and reads back a Proposed replacement, then returns Candidate to `Need Call Candidate` and writes Status History. The Proposed row is not displayed as active while the BSO re-contacts the Candidate. After the Candidate returns through Answered to Waiting Manual Scheduling, the BSO must explicitly reselect the TA and Location and re-enter the date/time; the existing Proposed row is confirmed and promoted to Scheduled instead of creating a duplicate. Candidate `CAND-00001023` completed this reschedule/re-contact/reconfirmation loop. After reload, its Superseded and Scheduled rows, lifecycle evidence, Candidate state (`Round 1 Scheduled`), and history remained visible.

For cancellation, the UI requires a reason, marks the existing schedule Cancelled with a lifecycle timestamp, confirms readback, returns Candidate to `Need Call Candidate`, writes Status History, and refreshes. Candidate `CAND-00001024` remained `Need Call Candidate`; its Cancelled schedule, reason/time, and history remained visible after a full browser reload. The two Candidates reconcile to Candidate / Call Log / Status History / Interview Schedule / Receipt = **2 / 3 / 11 / 3 / 0**.

Browser writes remain nontransactional DEV technical debt. A saved schedule state is never deleted as compensation; on later Candidate or Status History failure, the UI surfaces a safe warning and refreshes server truth, without automatic retry, compensation, or fabricated history.
