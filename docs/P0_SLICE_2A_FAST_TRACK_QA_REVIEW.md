## Independent challenge findings

### C1 — Blocker: a supported conditional, solution-aware OFF Flow update is not established

The Stage A report captured an SDK `RowVersion`; it did **not** demonstrate an HTTP ETag, a documented equivalent precondition for this Flow, or a supported conditional update of only the existing solution-aware Flow. Do not equate `RowVersion` with an HTTP ETag or assume that a general record PATCH is supported for this exact `clientdata` update. The public Microsoft Learn article *Work with cloud flows using code* documents a general Workflow PATCH; its example uses `If-Match: *` and changes the Flow to ON. The wildcard does not protect against intervening versions and the example does not prove a single-Flow, solution-aware, OFF-preserving update. A whole-Solution import likewise has not demonstrated the required component closure or concurrency protection.

**Gate:** Before any separately approved write, prove a supported authoring/ALM surface and its exact-version ETag or documented equivalent, including applicable optimistic-concurrency support for the selected operation. Independently revalidate the exact organization, unmanaged Solution, one existing Flow, owner, connection references, OFF state, current definition and version, and relevant topology. Retain the actual decoded pre-update definition and its hash under approved access/retention controls. Show that the proposed semantic delta contains only the approved `secureData` settings and that membership, identity, owner, connections, trigger, actions, retries, and state are preserved. Dispatch the one bounded update once, with no automatic retry; independently reconcile exact definition, metadata, membership, and OFF state. Stop on a 412, timeout, lost response, unexpected delta, or any uncertain outcome. Read-only reconciliation is not permission to replay. If the supported precondition cannot be demonstrated, do not write.

**Rollback:** A restore is a separate, explicitly authorized change using the retained definition, a newly observed version, the same proven concurrency protection, and an independently reviewed diff. Do not blindly overwrite later edits, auto-restore after an ambiguous response, or activate the Flow as a recovery step.

### C2 — High: the Console delta is small, but the old helper and hash-only evidence do not establish a safe repair

The six authored hashes in the Stage A table were checked against current repository bytes. The table records equal published, current/unpublished, and app-served hashes for each of the six resources; the authored environment template intentionally differs from the bound environment resource. This is a cross-check of recorded evidence, **not** a fresh tenant read. The [generator](../scripts/New-BsoRsCandidateConsoleEnvironmentConfig.ps1) derives the HTML query token from the first 12 hexadecimal characters of the bound configuration hash.

Using the recorded bound configuration hash, an in-memory substitution of only `39135f67e4c9` with `58e03dc262b7` in the authored HTML produced SHA-256 `699afe50dc3a1bb898ddb3cac301edc36b3bb7a861429dfad5e50b5158403e25`; reversing that substitution reproduced the original bytes and SHA-256 `b0d3cede68669fc4bc080100a3318d433cd116b159cee32f8d96f20bd086086e`. This supports the proposed token-only correction, not its authorization or future applicability if the target changes.

The [older deployment helper](../scripts/Deploy-BsoRsCandidateConsole.ps1) hard-codes a five-resource inventory and omits the Availability script from its `ValidateSet`; the present source inventory has six. Its publish-only path requires the old five and rejects replacement content. A refresh branch constructs WebResource-only publication XML, but another branch includes the app module. Therefore, neither the helper as a whole nor an assumed mode establishes a safe exact-one-resource repair; do not bypass its inventory checks.

**Baseline challenge:** The retained `rw-preflight.json` resource entries inspected contain identifiers, names, types, and hashes, not recoverable content; the inspected `rw-final.json` Console summary contains hashes for two changed resources. The Stage A table provides six-resource layer hashes. These inspected artifacts do not establish that actual, restorable **current and published bytes for all six** were retained. This is not a claim that no other protected snapshot exists.

**Gate:** For a separately authorized correction, first obtain and independently hash the actual immediately preceding published and current/unpublished bytes, identities, versions, and membership for all six, preserving any differing layers separately in approved protected storage. Establish an audited, exact one-HTML-resource PATCH and one-resource publication procedure that accounts for all six resources without publishing the app, sitemap, or other resources. Bind any update to fresh supported concurrency evidence. Reconcile both layers and the other five resources afterward. Published readback alone does not establish app-served freshness; if an authenticated served-byte check is required, separately approve its browser, privacy, and automatic-request effects as described in C3. Stop and read back after an ambiguous PATCH or publish; do not automatically repeat either. Approve a separate rollback that can restore the prior published layer **and** any distinct unpublished layer without clobbering concurrent changes; stop if that outcome cannot be proven. Do not store target configuration or captured bytes in the repository.

### C3 — High: service-worker and browser effects remain bounded unknowns

All six historical app responses were service-worker-served. That session received the recorded current configuration even with the old token; no stale configuration was observed there. A changed query token distinguishes a request URL, but it does not prove that every service worker or client respects that distinction, refreshes the HTML, or serves fresh bytes. The absent `availabilityEnabled` value disabled the observed controls; a UI gate is not an authorization or server-side security boundary.

The historical startup counted four Dataverse non-GET requests and three other non-GET requests. A later passive audit named three Dataverse POST paths: `msdyn_ReportToMonitoringHub`, `GetRecentItems`, and `GetCopilotSettingsForEnvironment`. The two observed sets are not proven identical. Bodies, responses, persistence, the fourth Dataverse endpoint, and the other endpoints remain unknown. Equal aggregate row counts cannot rule out updates, offsetting changes, telemetry, audit entries, or other effects. No Candidate business action was deliberately invoked; neither zero effects nor a Candidate mutation is established.

**Separate decision:** This browser uncertainty does **not independently** block a genuinely isolated, separately approved Flow-only OFF change that does not start the browser or invoke Candidate/Outlook operations. It also does not close the drift, grant permission, override an audit/privacy/owner objection, or make official Stage B ready: the correction or an explicit owner-approved exception and the remaining Flow gates are still required. An organization may decide that unresolved effects block even that isolated change.

For any later browser or platform access, approve the specific bounded operations and their possible automatic telemetry/audit effects in advance. Review privacy and auditing, avoid collecting business content, record only necessary sanitized evidence, and stop on unexpected operations. Do not assume a nominally observational platform action has zero non-GET side effects.

### C4 — High: serialized privacy settings are not runtime privacy acceptance

The Stage A report states that the historical live Flow matched the pre-hardening source; this QA did not reread it. An independent comparison of the historical repository Flow at Git revision `7a64022e1891607b9d4c789d0f03e1c99640df88` (SHA-256 `f901baae0abc5f2a2eccf74bf59e76fe05189a6e13bf86a981d6d6e4dbeb8811`) with the [current source](../solutions/AvailabilityQuery/os_sr_avchk.clientdata.json) (SHA-256 `0e1a1de9cfece98440b1ec8b52dcd76648a25826a06bcf36fafcefbb39c701b0`) found exactly 26 structural changes, all in `runtimeConfiguration.secureData`; removing only those settings and resulting empty containers makes the parsed sources identical. Of the [contract](../solutions/AvailabilityQuery/availability-flow.contract.json)'s 32 sensitive actions, the historical source has 19 without settings, five with inputs only, and eight with inputs and outputs. The current source protects both inputs and outputs for all 32, adds protection to `Set_location_changed` outside that inventory, and protects trigger outputs.

1. **Gate 1 — local serialization:** source-level settings and recursive tests exist; this is not a platform observation.
2. **Gate 2 — acceptance and readback:** after a separately authorized OFF update, prove that the platform accepts and retains the intended trigger setting and every applicable action setting, including the additional action. Compare the entire definition and preserve OFF. Passing Gate 2 does not prove obscuring in run history.
3. **Gate 3 — runtime obscuring:** only after independent runtime, identity, mailbox, and privacy approvals, use controlled synthetic runs and inspect authorized run-history views to verify actual suppression for executed sensitive paths. A single successful run cannot exercise mutually exclusive success/failure, online/onsite, or all nested paths. Define the separately approved scenario coverage and retain sanitized results without raw addresses, free/busy payloads, or other personal data.

The elevated development Flow owner is not a least-privilege acceptance identity. No synthetic run or run-history inspection was performed in this QA.

### C5 — High: the 429 contract and recursive no-retry implementation need an owner decision

The [Flow contract](../solutions/AvailabilityQuery/availability-flow.contract.json) says to honor `Retry-After` with **at most two** retries for the idempotent provider read, only within an overall request deadline. The recursive source inspection found `retryPolicy.type = none` on all seven nested `OpenApiConnection` actions, including the provider read and terminal result write; the webhook trigger does not declare an explicit retry policy. The [tests](../tests/AvailabilityQuery.Tests.ps1) independently assert the contract text and the no-retry connector settings, so their passing separately would not settle the intended end-to-end policy.

Zero is mathematically within “at most two,” so the text alone does not unambiguously require a retry. Nevertheless, it does not clearly settle whether a throttled read should be retried or surfaced immediately, and no `Retry-After` retry/deadline mechanism was established in the inspected Flow. The provider action's `PT2M` timeout is not proof of an overall retry deadline. The source maps a provider 429 toward `PROVIDER_THROTTLED`, but actual runtime behavior, reference-drift precedence, and success of the terminal write remain unverified.

**Recommendation:** Retain no automatic connector retry pending a recorded owner/Technical Lead decision. Decide explicitly whether 429 terminates as a safe throttled failure or permits a bounded provider-read retry; align the contract, implementation, and recursive tests in a separately approved change. If retries are chosen, specify supported `Retry-After` handling, a total deadline, attempt limits, and safe behavior for all failure paths. Never infer exactly-once behavior from trigger concurrency, and never blindly retry an ambiguous terminal result write. Verify any claimed final status under separately authorized synthetic runtime scenarios.

Separately authorize least-privilege security acceptance with a clean BSO/requester and an approved writer: test allowed own-query creation/read, denied unauthorized result writes and cross-user access, no added Candidate Core privileges, and server-side guard enforcement. Review DLP, audit, connection consent, mailbox access, and separation of duties. The elevated development owner proves neither least privilege nor security acceptance.

## Authorization and acceptance boundaries

- Each prospective activity requires its own owner-approved scope, operator, independent reviewer, least-privilege identity, change window, evidence handling, stop conditions, and rollback decision. Approval for a Flow-only OFF update is not approval for Console publication, activation, registration, mailbox use, role assignment, or Candidate operations.
- Before a later authorized operation, revalidate time-sensitive target, Solution membership, Flow state/definition, resources, guards, roles, configuration, and feature gate. Treat unexpected drift as a stop, not an invitation to widen scope.
- Retain protected before/after evidence and verify it independently. Do not treat a hash as a recoverable backup, a 2xx response as complete reconciliation, or an unknown outcome as a failed operation. Platform audit/telemetry and any approved non-GET effects remain within the change review.
- Preserve the [production rules](../MASTER_PRODUCTION_RULES.md), [workflow](../WORKFLOW.md), and [project rules](../PROJECT_RULES.md). Keep ATSugg intact until separately approved migration acceptance and cutover.
