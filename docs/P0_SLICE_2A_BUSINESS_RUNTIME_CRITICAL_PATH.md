## 2. Source-derived result and action contract

### Persisted results are not guard exceptions

The [state enum](../solutions/AvailabilityQuery/AvailabilityRules.cs#L12-L24) is exact:

| Persisted `os_sr_avq_stat` | Reason `os_sr_avq_rsn` | Error `os_sr_avq_err` | Slots `os_sr_avq_slts` |
|---|---|---|---|
| Pending `100000000` | Not a terminal result | Not a terminal result | Not a usable result; create guard sets only Pending |
| Available `100000001` | `null` | `null` | Nonempty canonical UTC array |
| NoSlots `100000002` | `NO_COMMON_SLOT` | `null` | Exactly `[]` |
| Failed `100000003` | `null` | One allowlisted error | Exactly `[]` |

The [create guard](../solutions/AvailabilityQuery/AvailabilityQueryPlugin.cs#L54-L95) rejects invalid requests synchronously before persistence; it does **not** create a Failed row. It permits only six input fields and sets Pending itself. Missing/unreadable lookup rejection can be `INVALID_REFERENCE`/`REFERENCE_READ_FAILED`, not an invented terminal status. Required UTC Kind failures are `INVALID_REQUEST` ([transport check](../solutions/AvailabilityQuery/AvailabilityQueryPlugin.cs#L239-L245)).

For an admitted row, [terminal composition/write](../solutions/AvailabilityQuery/os_sr_avchk.clientdata.json#L1564-L1624) submits only state, reason, error, slots, queried-at and expiry, using `UpdateOnlyRecord`. The [update guard](../solutions/AvailabilityQuery/AvailabilityQueryPlugin.cs#L98-L155) requires the configured writer to be both caller and initiator, the existing state Pending, canonical JSON and consistent terminal fields. Available independently rechecks slot eligibility; NoSlots/Failed do not re-read reference business fields in the guard.

**Clock/expiry:** On provider success, `v_queriedAt` is captured after the call ([Flow](../solutions/AvailabilityQuery/os_sr_avchk.clientdata.json#L807-L831)); that same instant drives lead filtering. If still empty on failure, terminal composition uses its own `utcNow()`. Expiry is that queried-at plus configured `v_expMinutes`; initialization is **1 minute**, replaced only after valid configuration ([initialization](../solutions/AvailabilityQuery/os_sr_avchk.clientdata.json#L258-L274), [binding](../solutions/AvailabilityQuery/os_sr_avchk.clientdata.json#L531-L563)). Thus configuration-failure paths may propose one-minute expiry, not the intended environment expiry. Guard acceptance requires UTC Kind, expiry strictly later than queried-at and at most configured expiry + 1 second; it does not demand exact equality or automatically age the row. The [Console](../solutions/CandidateConsole/WebResources/os_/bso/candidate-console-availability.js#L146-L191) checks expiration before displaying a terminal result; expired/missing/invalid expiry is not a new persisted state and does not authorize scheduling.

**Slots:** [eligibility](../solutions/AvailabilityQuery/AvailabilityRules.cs#L297-L322) requires exact requested duration, 15-minute boundaries, requested-window containment, post-provider lead time, same Vietnam local day and configured business hours. [Canonical serialization](../solutions/AvailabilityQuery/AvailabilityRules.cs#L324-L392) permits only sorted distinct `startUtc`/`endUtc` objects, seconds plus `Z`, at most 200 slots and 32,768 characters. The Flow uses [WDL union/sort/string](../solutions/AvailabilityQuery/os_sr_avchk.clientdata.json#L1116-L1200); offline C# serialization is not proof of those platform expressions.

**Count convention for the matrix:** `C/P/T` means query-create attempts / Outlook action attempts / terminal-update attempts, excluding read-only polls and plug-in internal reads. One normal Online run has **5 connector actions**: Read_query, Read_ta, Find_meeting_times, Reread_ta, Write_terminal_result. Onsite adds Read_location and Reread_location, making **7**. Each admitted normal row adds one query row and one terminal update, not two terminal writes. Count actual attempts separately from acknowledged persistence. All rows require **zero Candidate/Core, os_sr_intv, Call, History, Receipt, email or calendar-event business mutations**; test-window preparation by an operator is a separately approved activity, not a Flow side effect.

## 5. Failure and retry decision boundary

**Recommend zero automatic retries for the first bounded runtime only, subject to owner/Technical Lead disposition of the contract wording.** This is safe fail-closed for availability reads only when faults actually reach their mapping and a terminal write succeeds; it is not guaranteed liveness. All seven nested connector actions currently specify `retryPolicy.type="none"`: Read_query (L388), Read_ta (L607), Read_location (L663), Find_meeting_times (L800), Reread_ta (L1382), Reread_location (L1453), Write_terminal_result (L1621) in the [Flow source](../solutions/AvailabilityQuery/os_sr_avchk.clientdata.json). The webhook has concurrency 1, but no explicit retry policy; no transport/connector/trigger exactly-once claim follows.

The [contract](../solutions/AvailabilityQuery/availability-flow.contract.json#L134-L139) says honor Retry-After with at most two retries inside an overall deadline. Zero is within the numerical ceiling, but the Flow has no demonstrated Retry-After/deadline retry mechanism. Its provider `PT2M` is an action timeout, not an overall-request deadline. Keep current source unchanged; owner must explicitly decide first-run throttling terminates as `PROVIDER_THROTTLED` or commission a separately approved contract/implementation/test alignment. This document does not approve ignoring a contract or adding retries.
