# Candidate Core server operations

Source for Candidate Core plug-in code used by the legacy signed `os_sr_cact` assembly and the unsigned package-backed `os_sr_cact` assembly, version `1.0.0.0`. This is authored .NET plug-in source, **not an exported/unpacked Solution**. The supported target is .NET Framework 4.6.2 with `Microsoft.CrmSdk.CoreAssemblies` pinned to 9.0.2.60; the SDK assembly is supplied by the Dataverse sandbox. No runtime dependency is merged/uploaded with the package assembly.

**Deployment status (2026-11-11):** assembly 1.0.5.0 and the enabled persistent profile are installed; conditional disable/restore readbacks passed. The existing `os_sr_siso` current XML value supports a strictly versioned alternative to the legacy expiry-bound profile. Keep the eight existing organization/environment/actor/scope/Position/Source/TA/Location GUID attributes unchanged; replace only `expiresUtc` with `profileVersion="2" lifetime="PersistentDev" enabled="true"`. This mode is accepted only for the existing server-pinned DEV organization. There is **no expiry date or far-future sentinel**. The actor remains the designated non-admin BSO, never the administrator. `enabled="false"` revokes the profile. Missing/invalid `enabled`, unknown versions/lifetimes/attributes, any expiry attribute in persistent mode, missing bindings or configuration all fail closed. The v2 `ScopedCandidateCoreApi` proof contract is unchanged: proofs last at most two minutes, Calendar is disabled, and every new verifier or protected business operation loads the current server profile and repeats existing eligibility checks. No profile value is cached server-side. Revocation prevents new authorization after the update is committed; it does not cancel already-running transactions or erase a previously issued browser proof. A browser can display its prior proof until its short TTL, but the Console refreshes proof before business dispatch and the server independently rechecks every protected operation. Native access, administrator powers and other actors are not newly isolated or expanded. This profile is not lifecycle or real-data authorization.

**Direct administrative revocation:**

Verification returns before the business request adapter/store and never looks up or creates a receipt. Only declared optional parameters' typed empty transport defaults (including `DateTime.MinValue`) are ignored; non-default business inputs, a supplied non-empty `SyntheticScopeId`, and unknown parameters are rejected. **Scoped API proof revision (2026-11-10; supersedes the verifier requirements below):** `VerifySyntheticIsolation` now returns contract **v2**, explicitly named `ScopedCandidateCoreApi`, not full isolation of the organization or every data channel. New caller-owned rows need the existing Basic Read; SYSTEM-owned receipts do not require caller Receipt Read. No guard registration or Search/TDS/change-tracking condition is used by this proof.

The verifier denies protected native Create/Write/Delete/Assign/Share, Receipt Read, bypass, impersonation, customization import/publication and role/user/team/profile/API/plug-in control-write grants. Normal unrelated app/user-setting privileges are not a full-organization allowlist failure. These checks repeat on **each scoped business operation**, so a cached browser proof cannot authorize a request after privilege/profile/API drift. Exact scope, identity/owner/reference validation, transaction, row-version and receipt checks remain in force. The read-only verifier makes no business/history/receipt writes. Its two-minute proof is bounded by the profile expiry, always disables Calendar, and is not lifecycle authorization.

The Console consumes only this explicit v2 boundary, narrows Candidate/reference queries to proof IDs, refreshes proof before every business dispatch, and disables controls on refresh denial. This client narrowing is not a native-read authorization boundary: BSO-owned/shared records and Global-readable references may remain accessible outside the Console, and administrators/other actors are not isolated. The legacy full-guard helpers below remain source/history only; they are not prerequisites for this scoped proof and must not be deployed as 82 steps.

Required deployment delta: separately versioned corrected package, existing optional `SyntheticScopeId` Guid input plus `IsolationContract` string output, exact protected `os_sr_siso` definition/current XML value, and HTML/main/policy WebResources. Preserve the target-bound environment, disabled availability and CSS; never publish the unconfigured template. The prior 1.0.2 artifact is retained unchanged. ## Phase 5B storage-boundary correction (29 October 2026)

The source audit proved that Candidate Core's protected Candidate and Interview Schedule reads used the initiating-user service even though the corresponding writes and Receipt operations used SYSTEM. ## Runtime boundaries

- `ApplyCandidateAction` is the synchronous main-operation handler for the unbound private Action `os_sr_cact`. Private affects discovery, not authorization.
- The plug-in context remains the initiating caller and rejects mismatched or nested execution. The handler validates request inputs and caller-visible references with the initiating-user service, then creates the SYSTEM organization service with `CreateOrganizationService(null)`.
- SYSTEM access is confined to `ApplyCandidateAction` and its fixed operation store. All protected Candidate, Call Log, Status History, Interview Schedule, and Operation Receipt reads/writes use SYSTEM; Candidate and full Schedule reads verify the initiating user's effective `ReadAccess` through `RetrievePrincipalAccess` first. Schedule discovery queries return IDs only before the access check. Reference-table reads remain caller-context. The store exposes no caller-provided table, entity, message, or attribute names, and mutations remain constrained by `CandidateOperation.MutationMatrix`.
- The production BSO role must not receive direct Create/Write on protected business tables. Phase 5A readback in VN LMV IT confirmed live `os_sr_cact` uses `prvReados_sr_cand`; at that time the BSO role was unassigned. Phase 5B later assigned the role directly to the approved test identity. Protected-table Create/Write grants remain absent, but effective non-admin security acceptance is still pending.
- Organization-level auditing remains an external governance/release prerequisite, but it is not a Candidate Core runtime rejection. Required table-audit metadata and the append-only Status History/Operation Receipt business evidence remain mandatory. This does not enable or change organization auditing or waive governance gates for production rollout.
- Candidate creation/profile updates, the three call outcomes, Waiting Manual Scheduling, Round 1 scheduling, Pass/Fail, reschedule, and cancellation are implemented and offline-tested. Phase 5A runtime and browser lifecycle acceptance in VN LMV IT passed the scope recorded in the [acceptance report](../../docs/PHASE_5A_CANDIDATE_CORE_ACCEPTANCE_REPORT.md); this does not add browser acceptance for profile updates. The existing `os_sr_intv` Round 1 schedule is authoritative durable evidence for the manual Candidate Core workflow; active caller-readable TA and Location references and a valid future same-day UTC interval are required. Schedule persistence is read back before Candidate, Status History, and Receipt changes. Pass/Fail requires exactly one active Round 1 schedule without a terminal result. Reschedule/Cancel require that schedule plus a reason, preserve schedule history, and return Candidate to Need Call Candidate.
- The manual `os_sr_intv` record is workflow evidence, not proof of an external calendar booking or live calendar availability. This does not bypass the separate identity and fail-closed rules for any future Microsoft 365 calendar or email integration.
- Present profile fields replace, omitted fields preserve, and explicit null clears optional phone/lookups only. Name/email cannot be blank/null. UTC contact timestamps cannot be in the future.
- Versioned canonical request fingerprints include caller, correlation identity, action, target, expected status, and all supplied validated fields. Omission/null/type boundaries are distinct. Digests remain sensitive evidence, not anonymization.
- Receipt insert and applicable Candidate/Call/History effects share the caller's synchronous Dataverse transaction. Unique canonical-string correlation key prevents racing duplicate effects; transaction faults propagate without internal retry. An exact later replay returns persisted original effect IDs/status even after subsequent Candidate edits.
